01 / THE PROBLEM

A redirect is not trust.

Single sign-on is a protocol integration problem, not just a login button. Both sides need matching metadata and identifiers, a correctly addressed response, and a certificate trust arrangement that can be validated.

FLOW A / IDP-INITIATED

Identity provider to application

The IdP creates a SAML response and sends it to the Service Provider, which processes the response and establishes the application session if validation succeeds.

FLOW B / SP-INITIATED

Application to IdP / ADFS

The application starts an authentication request, redirects the user to the IdP, and receives the resulting SAML response at its configured assertion consumer endpoint.

02 / ENGINEERING WORK

Define the trust boundaries.

The public repository documents both IdP-to-SP and SP-to-IdP flow handling, metadata generation, certificate/key use, and SAML message signing or verification.

01 / MESSAGE STRUCTURE

Identifiers and endpoints

  • Issuer and entity identifiers for the participating systems.
  • Subject / NameID and assertion consumer service (ACS) destination.
  • Audience restriction and recipient context.
02 / CRYPTOGRAPHIC TRUST

Metadata and certificates

  • SAML metadata for endpoints and certificates.
  • X.509 certificate and private-key handling for message signing.
  • Verification of incoming SAML signatures against the trusted IdP certificate.
Engineering note: This is a public demonstration repository, not a claim that every production-hardening control is enabled. Review the actual code and configuration before reusing it in a production identity system.
03 / SECURITY REVIEW

What I would verify before production.

These are the review points to validate for a real deployment; they should not be read as a claim that every control is fully implemented in this demo.

  • Validate signature trust and the allowed signing certificate.
  • Check issuer, audience, recipient, and destination consistency.
  • Enforce assertion validity windows and clock-skew policy.
  • Prevent assertion replay and unintended session creation.
  • Keep private keys and IdP secrets outside the repository.
  • Avoid logging raw assertions, tokens, or authentication secrets.
04 / TAKEAWAY

Security is in the details.

This project demonstrates protocol-level integration work: understanding the SAML message exchange, configuring the trust relationship, and treating validation as the boundary between an external identity and an application session.
